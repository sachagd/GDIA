Key insight: don’t reinvent “hitbox extraction”

You provided the full code of EclipseMenu ShowHitboxes.cpp.

The critical parts we extracted from that file:

Correct way to iterate nearby objects is via GJBaseGameLayer::m_sections spatial grid with indices:

m_leftSectionIndex..m_rightSectionIndex, m_bottomSectionIndex..m_topSectionIndex

and cell sizes via m_sectionSizes[i]->at(j)

This is why your earlier approach using collisionBlocks produced junk (like only object id=1816 that wasn’t near / not in the level).

Correct hitbox geometry sources (same as Eclipse):

If available: use oriented box (play uses obj->m_orientedBox, editor uses obj->getOrientedBox()), corners = m_corners[0..3]

Else: use axis-aligned hitbox via obj->getObjectRect()

For hazards: sometimes use circle hitbox with radius = max(scaleX, scaleY) * obj->m_objectRadius

Important subtlety: calling getObjectRect() can mutate internal state, so Eclipse saves/restores:

m_isObjectRectDirty

m_boxOffsetCalculated
We mirrored that in our code to avoid side effects.

Filtering used by Eclipse (for relevance / avoiding junk):

skip Decoration

skip not activated / disabled groups

skip player objects themselves

Working prototype 2: occupancy matrix (grid) from hitboxes

You asked how to handle objects with different shapes/sizes (thin bars vs circles).

Key answer: no ID-based hacks needed because we already have the real collision geometry (AABB/OBB/circle) from game data.

We implemented a basic occupancy grid:

Choose a world window around player: [px - backX, px + frontX] × [py - halfY, py + halfY]

Fixed grid size: W × H

Rasterize by scanning only cells within each shape’s bounding box and checking cell center inside shape:

circle: point-in-circle

OBB: point-in-convex-quad (using cross products)

AABB: point-in-rect

Grid values stored as 0/1.

You wanted to see the matrix, not logs, and you’re on Linux (Steam Proton).

Real-time matrix display method that worked: write to file + watch

Instead of console output, we implemented:

write matrix text to a file each N frames (to limit IO)

Known current limitation discovered

Very thin bar hitboxes (thin floor/wall/ceiling pieces) are rarely marked in the matrix even when visible.

Why: current rasterization uses single sample per cell (cell center), so thin shapes can fall between centers.

You tried halving FOV to increase resolution (grain), but it made the view too zoomed-in and still didn’t fully solve it.

We brainstormed non-code solutions for later:

multi-sample per cell (center + corners, or 3×3)

shape-vs-cell intersection tests (best for AABB thin bars)

inflate hitboxes slightly during rasterization

internal higher-res grid + max-pool downsample to fixed CNN input size
